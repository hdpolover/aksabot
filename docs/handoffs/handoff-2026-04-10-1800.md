**Session: Display + Touch + WS + Audio pipeline — near end-to-end**

## Status

Display, touch, face expressions, WebSocket connection, and audio recording all working. The voice pipeline is connected end-to-end but **binary Opus frames are not reaching the backend** — the last remaining gap before voice round-trip works.

### What was done this session

#### Firmware
1. **TFT_eSPI → LovyanGFX** — full display driver swap with runtime config
2. **Touch rewrite** — replaced manual FT6336G I2C with LovyanGFX `Touch_FT5x06`, INT pin gating, debounce
3. **Face expressions** — 10 visually distinct expressions (unique eye shapes, mouths, decorations per state)
4. **Touch visual feedback** — tap/hold/wake produce visible face reactions

6. **Audio capture stack** — increased 8KB → 24KB (Opus encoder needs ~10-15KB)
7. **Power manager fix** — uint32 underflow guard in tick()
8. **Touch hold fix** — LONG_PRESS increased to 5s, HOLD_END always fires, LONG_PRESS ignored during recording
9. **Stuck state recovery** — 15s timeout auto-reverts THINKING/LISTENING to IDLE
10. **Backend error handling** — firmware handles `error` and `state:update` events from backend

#### Backend
1. **STT stream race fix** — `onAudioEnd` nulls `sttStream` before calling `end()` to prevent late chunk writes
2. **Error flood fix** — STT error handler nulls stream on first error to stop cascade
3. **Audio path simplified** — removed async Redis rate limiter, decode+write is fully synchronous
4. **Greeting timing** — fire-and-forget but suppressed during active recording
5. **Debug logging** — chunk count, Opus→PCM decode sizes

### What's working
- **Display**: LovyanGFX ILI9341, sprite-buffered 30fps, PWM backlight
- **Touch**: clean TAP, HOLD_START/END, LONG_PRESS, WAKE — all reliable
- **Face**: 10 distinct expressions with visual feedback on touch
- **WebSocket**: stable single connection, mutex-protected, reconnects in ~1s after disconnect
- **Audio recording**: mic reads → Opus encode → frames ready to send (stack watermark: 50KB free of 24KB)
- **Backend receives events**: `audio:start` and `audio:end` arrive cleanly
- **STT pipeline configured**: Google Cloud Speech, Opus→PCM decode produces correct 640-byte frames

### What's NOT working — binary Opus frames not reaching backend

**The critical gap**: firmware encodes Opus frames and calls `sendBinary()`, but the backend receives zero binary frames. The firmware's `sendBinary()` uses a 10ms mutex timeout — if the WS poll task holds the mutex (50ms timeout for poll), binary sends silently fail.

**Root cause hypothesis**: the audio capture task (Core 0) calls `sendBinary()` which needs the mutex, but the WS poll task (Core 1) holds it during `client.poll()` or `client.connect()` which can block for network I/O.

**Fix approach**: either increase the `sendBinary` mutex timeout, queue frames for the poll task to send, or separate send/receive onto different mutex scopes.
