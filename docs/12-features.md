# 12 — Bot Features and Capabilities

---

## Overview

The bot has two interaction modes:

1. **Reactive** — user initiates (tap to talk, ask a question, give a command)
2. **Proactive** — bot initiates (reminders, ambient updates, scheduled behaviors)

Reactive features are the core of the product (Phases 1-3). Proactive features transform it from a voice assistant into a desk companion that actively helps you throughout the day.

---

## Reactive features (user-initiated)

### Voice conversation

The primary interaction. User taps screen, speaks, bot responds via the streaming audio pipeline.

| Feature | Description | Phase |
|---------|-------------|-------|
| General Q&A | Ask anything — facts, explanations, opinions | 1 |
| Language switching | Bot responds in whatever language you speak (ID/EN) | 1 |
| Rubber duck debugging | Explain your code problem out loud, bot asks clarifying questions | 3 |
| Quick capture | "Remind me to email the client" → stored as memory, retrievable later | 3 |
| Conversation continuity | "What were we talking about yesterday?" → memory bridges sessions | 3 |

### Voice commands

Short imperative commands that trigger specific actions rather than conversation.

| Command | What it does | Phase |
|---------|-------------|-------|
| "Set a timer for 25 minutes" | Starts a countdown, bot alerts when done | 3 |
| "Start a pomodoro" | 25 min focus → 5 min break cycle, managed by backend scheduler | 3 |
| "Stop" / "Cancel" | Cancels active timer or pomodoro | 3 |
| "What time is it?" | Bot speaks the current time | 1 |
| "Go to sleep" | Bot enters sleep mode (display off, low power) | 2 |
| "Show the clock" | Switch to ambient clock display mode | 2 |
| "Show your face" | Switch back to face display mode | 2 |

### Touch interactions

| Interaction | Behavior | Phase |
|-------------|----------|-------|
| Tap and hold | Start recording (touch-to-talk) | 1 |
| Release | Stop recording, send audio | 1 |
| Tap during playback | Interrupt bot's response | 1 |
| Touch while sleeping | Wake up | 2 |
| Long press (3s) | End conversation session explicitly | 2 |
| Swipe left/right (future) | Switch display modes (face → clock → status) | 5 |

## Proactive features (bot-initiated)

These are the behaviors that make the bot useful for a developer sitting at a desk all day. The backend scheduler pushes events to the ESP32 over WebSocket — the bot lights up, shows an expression, speaks a brief message, and goes back to idle.

### Health and wellness reminders

| Reminder | Default interval | What the bot does | Configurable |
|----------|-----------------|-------------------|--------------|
| **Stand up** | Every 60 min | Screen wakes, bot says "You've been sitting for an hour. Time to stand up and stretch." Face shows encouraging expression. | Interval, enabled/disabled |
| **Hydration** | Every 45 min | Brief reminder: "Drink some water!" with a cheerful face | Interval, enabled/disabled |
| **Eye break (20-20-20)** | Every 20 min | "Quick eye break — look at something far away for 20 seconds." Screen shows a 20s countdown. | Interval, enabled/disabled |
| **Stretch** | Every 90 min | "Time for a quick stretch. Roll your shoulders, stretch your wrists." | Interval, enabled/disabled |
| **Posture check** | Every 30 min | Gentle: "How's your posture?" — just a nudge, no lecture | Interval, enabled/disabled |

**Key design principle:** Reminders are generated by the LLM with personality, not hardcoded strings. Each time the backend triggers a reminder, it sends a short prompt to Gemini: "Generate a brief, friendly stand-up reminder. Vary the phrasing. Keep it under 15 words." This means the bot never says the exact same thing twice, which prevents reminder fatigue.

The TTS audio for common reminder variations gets cached (Redis + MicroSD), so after the first few days most reminders play from cache with zero API cost.

### Work rhythm

| Feature | What it does | Trigger |
|---------|-------------|---------|
| **Pomodoro timer** | 25 min focus → 5 min break → repeat. Bot announces transitions. After 4 cycles, 15 min long break. | User starts with voice command |
| **Focus mode** | Bot suppresses all non-urgent reminders for N minutes. Face shows a focused/quiet expression. Screen dims slightly. | User starts with voice command |
| **End of day** | "It's 6pm — time to wrap up. What did you get done today?" Bot listens, stores summary as memory. | Scheduled time (configurable) |
| **Morning briefing** | On first interaction of the day: "Good morning! Yesterday you mentioned you were working on the auth module. How's that going?" | First audio:start after a new calendar day |
| **Idle nudge** | If no interaction for 3+ hours during work hours, bot gently checks in: "Everything okay? You've been quiet." | Inactivity timer |

### Ambient display

When the bot is idle, the screen can show useful information instead of just a static face. The user can switch between display modes.

| Mode | What's shown | When active |
|------|-------------|-------------|
| **Face** (default) | Animated face with idle micro-animations, connection dot | Default mode |
| **Clock** | Large time display, date, next upcoming reminder, mini face in corner | User switches or auto after idle timeout |
| **Pomodoro** | Focus timer countdown, current cycle (e.g., "Focus 3/4"), progress bar | During active pomodoro session |
| **Reminder** | Full-screen reminder text + icon + countdown (for eye break timer, etc.) | During active reminder |
| **Status** | Wi-Fi signal, battery, uptime, today's conversation count, cache stats | User switches explicitly |

Display modes are managed by the ESP32 — the backend sends the data, the firmware decides how to render it.

### Emotion-driven face expressions

During speech, the bot's face expression changes per-sentence based on the emotional context of what it's saying. The LLM tags each sentence with an emotion, and the backend sends `face:expression` events between sentences.

| LLM emotion tag | Face expression | Visual | Voice modulation |
|-----------------|----------------|--------|-----------------|
| `[happy]` | HAPPY | Pink eyes, smile mouth, raised brows | Slightly faster, lively |
| `[excited]` | ENCOURAGING | Gold eyes, big grin, bounce | Faster, more expressive |
| `[calm]` | CALM | Green eyes, gentle mouth | Slower, stable |
| `[sad]` | SAD | Blue eyes, frown mouth | Slowest, subdued |
| `[confused]` | CONFUSED | Orange eyes, wavy mouth, floating "?" | Slightly slower, uncertain |
| `[focused]` | FOCUSED | Blue eyes, tight mouth | Normal, precise |
| `[sarcastic]` | ENCOURAGING | Gold eyes, smirk | Slightly slower, very variable |
| `[neutral]` | SPEAKING | Teal, default oval | No change |

Audio-reactive micro-animations during speech:
- Eyes widen on loud parts (1.1x scale), squint on quiet (0.92x)
- Blink suppression during energetic speech
- Eyebrow raise on sudden amplitude spikes (400ms)
- Subtle head-nod synced to amplitude
- Natural gaze drift while talking

### Context awareness

The bot knows the current time and optionally the local weather:

| Context | Source | How it's used |
|---------|--------|---------------|
| **Local time** | Server clock + device timezone setting | "It's 3am bruh, why are you still up?" — time-aware responses |
| **Weather** | Open-Meteo API (free, no key), 15min cache | "It's 28°C and cloudy, perfect coding weather" — opt-in via Integrations page |

Weather requires location permission in the Flutter app (geolocator). Lat/lon/timezone saved to device settings and used by backend prompt service.

### SHRUG expression

New expression shown when errors occur or the bot has no response. Head shakes left-right with pursed lips blowing a bubble. Replaces the old CONFUSED expression on errors. Plays for 3 seconds before returning to idle.

## Scheduler system (backend)

The scheduler is what powers all proactive behavior. It runs on the backend and pushes events to connected ESP32 devices over WebSocket.

### Architecture

│  ┌───────────────┐    ┌──────────────────┐           │

### Scheduler service

```typescript
// src/scheduler/scheduler.service.ts
@Injectable()
export class SchedulerService {
  private deviceTimers: Map<string, NodeJS.Timeout[]> = new Map();

  constructor(
    private devicesService: DevicesService,
    private reminderService: ReminderService,
    private gateway: AudioGateway,
  ) {}

  /**
   * Called when a device connects via WebSocket.
   * Starts all configured reminder timers for that device.
   */
  startDeviceSchedule(deviceId: string, config: ReminderConfig): void {
    const timers: NodeJS.Timeout[] = [];

    if (config.standUp.enabled) {
      timers.push(setInterval(
        () => this.fireReminder(deviceId, 'stand_up'),
        config.standUp.intervalMinutes * 60_000,
      ));
    }

    if (config.hydration.enabled) {
      timers.push(setInterval(
        () => this.fireReminder(deviceId, 'hydration'),
        config.hydration.intervalMinutes * 60_000,
      ));
    }

    if (config.eyeBreak.enabled) {
      timers.push(setInterval(
        () => this.fireReminder(deviceId, 'eye_break'),
        config.eyeBreak.intervalMinutes * 60_000,
      ));
    }

    // ... other reminders

    this.deviceTimers.set(deviceId, timers);
  }

  /**
   * Called when a device disconnects. Clears all timers.
   */
  stopDeviceSchedule(deviceId: string): void {
    const timers = this.deviceTimers.get(deviceId) ?? [];
    timers.forEach(clearInterval);
    this.deviceTimers.delete(deviceId);
  }

  private async fireReminder(deviceId: string, type: ReminderType): Promise<void> {
    // Don't fire if device is in focus mode or currently in a conversation
    const session = await this.getDeviceSession(deviceId);
    if (session?.state !== 'idle' || session?.focusMode) return;

    // Generate or retrieve reminder
    const reminder = await this.reminderService.generate(deviceId, type);

    // Push to device via WebSocket
    this.gateway.sendToDevice(deviceId, 'proactive:reminder', reminder);
  }
}
```

### Response pool system

Instead of calling Gemini for every reminder or greeting, bot responses are pre-generated in batches and stored in the `response_pool` database table. When a reminder fires, the system picks the **least recently used** response from the pool. This means:

- **Zero Gemini calls** for day-to-day reminders (pool serves everything)
- **Natural variation** — the pool has 10-20 variations per category, rotated by LRU
- **Personality-aware** — responses are generated using the device's personality config
- **Background refill** — when the pool runs low, new variations are generated during idle time

See [03-database.md](03-database.md) for the `response_pool` table schema.

#### How it works

```
Reminder fires (e.g., stand_up):
  1. Query response_pool: SELECT * FROM response_pool
     WHERE device_id = :id AND category = 'stand_up'
     ORDER BY last_accessed_at NULLS FIRST, last_accessed_at ASC
     LIMIT 1

  2. Pool has entries? → Pick LRU response, bump last_accessed_at and use_count
     Pool is empty?   → Fall back to Gemini LLM call (one-time, then store result)

  3. Look up TTS audio in Redis cache via tts_cache_key
     Cache HIT  → use cached audio (zero API cost)
     Cache MISS → synthesize via TTS, store in Redis + update tts_cache_key

  4. Send to ESP32 via WebSocket
```

#### Pool categories

| Category | Pool size | When generated | Example responses |
|----------|----------|---------------|-------------------|
| stand_up | 15 | Device setup + background refill | "Time to stand! Your legs will thank you." |
| hydration | 15 | Device setup + background refill | "Water break! Stay hydrated." |
| eye_break | 10 | Device setup + background refill | "Look at something 20 feet away for 20 seconds." |
| stretch | 10 | Device setup + background refill | "Quick stretch — roll your shoulders." |
| posture | 10 | Device setup + background refill | "Posture check! Sit up straight." |
| welcome_back_short | 10 | Device setup + background refill | "Welcome back!" / "Hey, you're back!" |
| welcome_back_long | 10 | Device setup + background refill | "Welcome back! You were away for a bit." |
| pomodoro_break | 8 | Device setup + background refill | "Nice focus session! Take a 5 minute break." |
| pomodoro_focus | 8 | Device setup + background refill | "Break's over — back to it! You've got this." |
| error | 5 | Device setup | "Something went wrong on my end. Try again?" |

**Personalized greetings** (morning briefing, long welcome-back with context) are NOT pooled — they need real-time memory context and are always generated via Gemini. Only the generic/repeatable ones are pooled.

### Reminder service (using response pool)

```typescript
// src/scheduler/reminder.service.ts
@Injectable()
export class ReminderService {
  constructor(
    private responsePool: ResponsePoolService,
    @Inject(TTS_PROVIDER) private tts: ITtsProvider,
    @Inject(TTS_CACHE) private ttsCache: ITtsCache,
    @Inject(AUDIO_CODEC) private codec: IAudioCodec,
  ) {}

  async generate(deviceId: string, type: ReminderType): Promise<ReminderPayload> {
    // 1. Pick LRU response from pool (or generate if pool is empty)
    const response = await this.responsePool.pickLru(deviceId, type);

    // 2. Get TTS audio (from cache or synthesize)
    let audio: Buffer;
    if (response.ttsCacheKey) {
      audio = await this.ttsCache.get(response.ttsCacheKey);
    }
    if (!audio) {
      const pcm = await this.tts.synthesize(response.text, { language: 'id-ID' });
      audio = this.codec.encode(pcm);
      const cacheKey = this.ttsCache.generateKey(response.text, 'id-ID');
      await this.ttsCache.set(cacheKey, audio);
      await this.responsePool.updateCacheKey(response.id, cacheKey);
    }

    return {
      type,
      text: response.text,
      audio,
      cacheKey: response.ttsCacheKey,
      display: REMINDER_DISPLAY[type],
    };
  }
}

const REMINDER_DISPLAY: Record<ReminderType, ReminderDisplayConfig> = {
  stand_up: { expression: 'encouraging', screenMode: 'reminder', durationMs: 10_000 },
  hydration: { expression: 'cheerful', screenMode: 'reminder', durationMs: 8_000 },
  eye_break: { expression: 'calm', screenMode: 'countdown', countdownSeconds: 20 },
  stretch: { expression: 'encouraging', screenMode: 'reminder', durationMs: 10_000 },
  posture: { expression: 'gentle', screenMode: 'reminder', durationMs: 5_000 },
};

### Response pool service

Manages the pool: LRU retrieval, background refill, batch generation.

```typescript
// src/scheduler/response-pool.service.ts
@Injectable()
export class ResponsePoolService {
  constructor(
    @InjectRepository(ResponsePool) private repo: Repository<ResponsePool>,
    @Inject(LLM_PROVIDER) private llm: ILlmProvider,
  ) {}

  /**
   * Pick the least recently used response for a category.
   * If pool is empty, generates one on the fly and stores it.
   */
  async pickLru(deviceId: string, category: string): Promise<ResponsePool> {
    // Get least recently used (NULLS FIRST = never-used responses are prioritized)
    const response = await this.repo.findOne({
      where: { deviceId, category },
      order: { lastAccessedAt: { direction: 'ASC', nulls: 'FIRST' } },
    });

    if (response) {
      // Mark as used
      response.lastAccessedAt = new Date();
      response.useCount++;
      await this.repo.save(response);
      return response;
    }

    // Pool is empty — generate one on the fly
    return this.generateAndStore(deviceId, category, 1).then((r) => r[0]);
  }

  /**
   * Generate a batch of response variations and store them.
   * Called during device setup and background refill.
   */
  async generateAndStore(
    deviceId: string,
    category: string,
    count: number,
  ): Promise<ResponsePool[]> {
    const prompt = POOL_GENERATION_PROMPTS[category];
    const { text } = await this.llm.generate(
      `You generate brief, friendly bot responses. Generate exactly ${count} variations, ` +
      `one per line. Each should be under 15 words. Vary tone and phrasing. No numbering.`,
      [{ role: 'user', content: prompt }],
    );

    const lines = text.split('\n').filter((l) => l.trim()).slice(0, count);
    const entries = lines.map((line) =>
      this.repo.create({ deviceId, category, text: line.trim() }),
    );

    return this.repo.save(entries);
  }

  /**
   * Check pool levels and refill categories that are running low.
   * Called periodically during device idle time.
   */
  async refillIfNeeded(deviceId: string): Promise<void> {
    for (const [category, targetSize] of Object.entries(POOL_TARGET_SIZES)) {
      const currentCount = await this.repo.count({ where: { deviceId, category } });
      if (currentCount < targetSize) {
        const needed = targetSize - currentCount;
        await this.generateAndStore(deviceId, category, needed);
      }
    }
  }

  async updateCacheKey(id: string, cacheKey: string): Promise<void> {
    await this.repo.update(id, { ttsCacheKey: cacheKey });
  }
}

const POOL_TARGET_SIZES: Record<string, number> = {
  stand_up: 15,
  hydration: 15,
  eye_break: 10,
  stretch: 10,
  posture: 10,
  welcome_back_short: 10,
  welcome_back_long: 10,
  pomodoro_break: 8,
  pomodoro_focus: 8,
  error: 5,
};

const POOL_GENERATION_PROMPTS: Record<string, string> = {
  stand_up: 'Generate stand-up reminders for someone who has been sitting at their desk coding.',
  hydration: 'Generate water/hydration reminders. Brief and friendly.',
  eye_break: 'Generate 20-20-20 eye break reminders (look 20ft away for 20 seconds).',
  stretch: 'Generate stretch reminders, mention shoulders, wrists, or neck.',
  posture: 'Generate posture check nudges. Gentle, not preachy.',
  welcome_back_short: 'Generate short welcome-back greetings for when someone returns to their desk.',
  welcome_back_long: 'Generate welcome-back messages that mention the person was away for a while.',
  pomodoro_break: 'Generate messages for starting a pomodoro break after a focus session.',
  pomodoro_focus: 'Generate messages for starting a new pomodoro focus session after a break.',
  error: 'Generate friendly error messages for when something went wrong.',
};
```

### Pool lifecycle

```
1. DEVICE PROVISIONED
   → Backend calls responsePool.refillIfNeeded(deviceId)
   → Generates initial pool for all categories (batch Gemini call)
   → Pre-generates TTS audio for each response (batch TTS call)
   → Stores tts_cache_key for each entry

2. DAILY OPERATION
   → Reminders/greetings served from pool via LRU
   → Zero Gemini calls, TTS from Redis/SD cache
   → Each response rotates: used → goes to back of LRU queue

3. BACKGROUND REFILL (during device idle)
   → Scheduler checks pool levels periodically (e.g., every 6 hours)
   → If any category is below target → generate missing entries
   → Pre-generate TTS audio for new entries
   → This happens silently, no user impact

4. PERSONALITY CHANGE
   → User updates personality/language in Flutter app
   → Backend clears the entire pool for that device
   → Triggers full refill with new personality
   → Also invalidates TTS cache (cache:invalidate event to ESP32)

5. POOL CLEANUP (optional, monthly)
   → Delete responses with high use_count (> 50) to force fresh variations
   → Refill runs automatically after cleanup
```

### Pomodoro service

```typescript
// src/scheduler/pomodoro.service.ts
@Injectable()
export class PomodoroService {
  private sessions: Map<string, PomodoroState> = new Map();

  async start(deviceId: string): Promise<void> {
    const state: PomodoroState = {
      cycle: 1,
      phase: 'focus',
      startedAt: new Date(),
      focusMinutes: 25,
      shortBreakMinutes: 5,
      longBreakMinutes: 15,
      cyclesBeforeLongBreak: 4,
    };
    this.sessions.set(deviceId, state);
    this.scheduleTransition(deviceId, state.focusMinutes);
    this.gateway.sendToDevice(deviceId, 'proactive:pomodoro', {
      action: 'start',
      phase: 'focus',
      cycle: 1,
      durationMinutes: 25,
    });
  }

  async transition(deviceId: string): Promise<void> {
    const state = this.sessions.get(deviceId);
    if (!state) return;

    if (state.phase === 'focus') {
      // Switch to break
      const isLongBreak = state.cycle % state.cyclesBeforeLongBreak === 0;
      state.phase = isLongBreak ? 'long_break' : 'short_break';
      const breakMinutes = isLongBreak ? state.longBreakMinutes : state.shortBreakMinutes;

      this.gateway.sendToDevice(deviceId, 'proactive:pomodoro', {
        action: 'break',
        phase: state.phase,
        cycle: state.cycle,
        durationMinutes: breakMinutes,
      });

      // Generate and send audio: "Nice work! Take a 5 minute break."
      const reminder = await this.reminderService.generatePomodoro(state);
      this.gateway.sendToDevice(deviceId, 'proactive:reminder', reminder);

      this.scheduleTransition(deviceId, breakMinutes);
    } else {
      // Switch to focus
      state.cycle++;
      state.phase = 'focus';

      this.gateway.sendToDevice(deviceId, 'proactive:pomodoro', {
        action: 'focus',
        phase: 'focus',
        cycle: state.cycle,
        durationMinutes: state.focusMinutes,
      });

      const reminder = await this.reminderService.generatePomodoro(state);
      this.gateway.sendToDevice(deviceId, 'proactive:reminder', reminder);

      this.scheduleTransition(deviceId, state.focusMinutes);
    }
  }

  stop(deviceId: string): void {
    this.sessions.delete(deviceId);
    this.gateway.sendToDevice(deviceId, 'proactive:pomodoro', { action: 'stop' });
  }
}
```

## WebSocket events for proactive behavior

New server-initiated events that the ESP32 handles:

| Event | Direction | Payload | Description |
|-------|-----------|---------|-------------|
| proactive:reminder | Server → ESP | `{ type, text, audio (binary), cacheKey, display: { expression, screenMode, durationMs, countdownSeconds? } }` | Health/wellness reminder with audio and display instructions |
| proactive:pomodoro | Server → ESP | `{ action: 'start'\|'focus'\|'break'\|'stop', phase, cycle, durationMinutes }` | Pomodoro state change — ESP32 updates display mode |
| proactive:briefing | Server → ESP | `{ text, audio (binary), cacheKey }` | Morning briefing or end-of-day prompt |
| proactive:nudge | Server → ESP | `{ text, audio (binary) }` | Idle nudge ("Everything okay?") |
| proactive:dismiss | ESP → Server | `{ type }` | User dismissed a reminder (tap during reminder) |
| proactive:snooze | ESP → Server | `{ type, snoozeMinutes: number }` | User wants to delay this reminder |
| face:expression | Server → ESP | `{ expression: string, durationMs?: number }` | Set face expression from backend (LLM sentiment). If durationMs is set, reverts to idle after timeout. Valid expressions: idle, listening, thinking, speaking, confused, sleeping, offline, encouraging, calm, focused, happy, sad |
| presence:arrived | ESP → Server | `{ awayDurationSeconds: number }` | User's phone detected after absence. Backend generates welcome-back greeting with TTS audio. Skipped if away < 5 min. First arrival of the day triggers morning briefing instead. |
| presence:departed | ESP → Server | (none) | User's phone lost. Backend sends `face:expression` sad. Firmware dims and sleeps display. |

### ESP32 handling of proactive events

```
proactive:reminder received:
  1. If device is sleeping → wake display
  2. Switch face expression to reminder type (encouraging, cheerful, calm, etc.)
  3. Switch screen mode if needed (reminder text overlay, countdown timer)
  4. Play audio (from cache if cacheKey matches local file, else from payload)
  5. After durationMs → return to previous display mode
  6. If user taps during reminder → send proactive:dismiss, return to idle immediately
```

### Smart scheduling

Reminders are aware of context:

| Context | Behavior |
|---------|----------|
| User is in a conversation | Don't interrupt — queue the reminder for after the conversation ends |
| Focus mode is active | Suppress all non-urgent reminders |
| Pomodoro focus phase | Suppress wellness reminders until break |
| Pomodoro break phase | Fire wellness reminders (good time to stand up) |
| **User is AWAY (BLE presence)** | **Suspend all reminders and timers. Resume when user returns.** |
| Device is sleeping (manual) | Don't fire reminders |
| Outside work hours | Don't fire reminders (configurable work hours: default 8am-6pm) |
| Just fired a reminder | Don't fire another one within 5 minutes (cooldown) |

## Morning briefing

The morning briefing is triggered on the first `audio:start` of a new calendar day (based on device timezone). The backend detects this and prepends a briefing to the normal response flow.

### How it works

```
1. User taps screen (first interaction of the day)
2. Backend detects: last session was yesterday → trigger morning briefing
3. Backend queries memories + yesterday's conversation summaries
4. Backend sends LLM prompt:
     "Generate a brief morning greeting for Hendra. Yesterday he mentioned
      he was working on the auth module and had a meeting with the mobile team.
      Ask how things are going. Keep it to 2-3 sentences."
5. Response plays as the first thing the user hears before their query is processed
6. Normal audio pipeline continues after briefing
```

The briefing feels natural because it's personalized via memories and recent conversation context.

## BLE presence detection (auto sleep/wake)

The bot detects whether you're at your desk by scanning for your phone's Bluetooth signal. When you walk away, it sleeps. When you come back, it wakes up and greets you. This makes the bot feel aware of you without any manual interaction.

### How it works

The Flutter app advertises a known BLE service UUID in the background. The ESP32 periodically scans for this UUID and reads the RSSI (signal strength) to estimate proximity.

```
Phone nearby (RSSI > -75 dBm)     → user is present → bot is awake
Phone weakening (RSSI -75 to -90) → user might be leaving → no action yet (hysteresis)
Phone gone (RSSI < -90 or absent) → user is away → bot sleeps after grace period
Phone reappears (RSSI > -75)      → user is back → bot wakes + greeting
```

### State machine

```
                    phone detected
    ┌──────────┐   RSSI > -75 dBm    ┌──────────┐
    │          │ ──────────────────> │          │
    │  AWAY    │                     │ PRESENT  │
    │ (sleep)  │ <────────────────── │ (awake)  │
    │          │   no signal for     │          │
    └──────────┘   grace period      └──────────┘
         │              ▲                  │
         │              │                  │
         │         ┌────┴─────┐            │
         └───────> │ LEAVING  │ <──────────┘
     (not used)    │ (grace   │   RSSI dropping
                   │  period) │   below threshold
                   └──────────┘
                   30-60s before
                   transitioning
                   to AWAY
```

Three states prevent flapping:

| State | Display | Reminders | Trigger to next state |
|-------|---------|-----------|----------------------|
| **PRESENT** | Active/normal | Firing normally | RSSI drops below -75 for 10+ consecutive scans → LEAVING |
| **LEAVING** | Still active (grace period) | Paused | RSSI recovers → PRESENT. No recovery for 30-60s → AWAY |
| **AWAY** | Sleep (screen off) | Suspended | Phone RSSI above -75 → PRESENT (wake + greeting) |

The grace period (LEAVING state) prevents the bot from sleeping every time you walk to the kitchen for 30 seconds.

### Wake greeting

When transitioning from AWAY → PRESENT:

```
1. ESP32 detects phone RSSI above threshold
2. Screen wakes, face shows happy/greeting expression
3. ESP32 sends presence:arrived event to backend
4. Backend generates personalized greeting via LLM:
     "Welcome back, Hendra! You were away for about 45 minutes.
      You have 2 reminders that fired while you were gone."
5. Bot speaks greeting + plays from cache if available
6. Resume normal operation (reminders, ambient display, etc.)
```

If the absence was short (< 5 min), the greeting is simpler: just a face wake-up animation, no spoken greeting (would be annoying for bathroom breaks).

| Absence duration | Greeting behavior |
|-----------------|-------------------|
| < 5 minutes | Silent wake — face lights up, no audio |
| 5-30 minutes | Short: "Welcome back!" (from cache, no LLM call) |
| 30+ minutes | Personalized: LLM-generated, mentions duration and missed reminders |
| Next calendar day | Triggers morning briefing instead of regular greeting |

### ESP32 firmware implementation

```
Module: presence_detector
  - presence_init(target_uuid, scan_interval_ms, rssi_threshold)
  - presence_get_state() → PRESENT | LEAVING | AWAY
  - presence_on_state_change(callback)
  - presence_get_rssi() → int8_t (latest smoothed RSSI)
  - presence_get_away_duration() → uint32_t (seconds since AWAY started)
```

**BLE scanning strategy:**
- Scan every 5 seconds for 2 seconds (duty cycle: 40%)
- Use passive scanning (less power than active)
- Only look for the specific app UUID — ignore everything else
- RSSI smoothing: rolling average of last 5 readings to reduce noise
- Runs on the existing BLE task (low priority, core 1)

**Power consideration:** BLE scanning at 40% duty cycle adds ~30mA. Acceptable on USB power. On battery, reduce scan frequency when in AWAY state (scan every 30s instead of 5s — just checking if phone came back).

### Flutter app: background BLE advertising

The app needs to advertise a known BLE service UUID even when in the background.

```dart
// Using flutter_blue_plus or flutter_ble_peripheral
class PresenceAdvertiser {
  static const presenceServiceUuid = '0000FFE4-0000-1000-8000-00805F9B34FB';

  Future<void> startAdvertising() async {
    await FlutterBlePeripheral().start(
      advertiseData: AdvertiseData(
        serviceUuids: [presenceServiceUuid],
        localName: 'AksaOwner',
      ),
    );
  }
}
```

**Platform considerations:**

| Platform | Background BLE advertising | Notes |
|----------|--------------------------|-------|
| Android | Works well | Use foreground service for reliability. Battery impact minimal (~1-2%). |
| iOS | Limited | iOS changes the advertised UUID in background. Workaround: ESP32 scans for the iOS-mangled UUID using the IRK (Identity Resolving Key) after bonding. Alternatively, scan by device name instead of UUID. |

**Recommendation:** Use BLE bonding between the phone and ESP32 during provisioning. This solves the iOS background UUID issue and adds encryption to the BLE link. The ESP32 stores the bonded device's identity and can resolve it even when iOS randomizes the address.

Added to `devices.settings_json`:

## Focus mode

When the user needs deep work time:

```
User: "Focus mode for 2 hours"
Bot: "Got it — focus mode for 2 hours. I'll keep quiet. Good luck."

During focus mode:
  - All wellness reminders suppressed
  - Display dims slightly
  - Face shows a calm/focused expression
  - Bot only speaks if user initiates
  - Pomodoro continues if active (timer transitions still fire)

After 2 hours (or user cancels):
  Bot: "Focus mode ended. You were focused for 2 hours. Nice work."
  - Reminders resume
  - Display returns to normal brightness
```

## Display modes (firmware)

The ESP32 display system needs to support multiple modes beyond just the face.

| Mode | Layout | Data source |
|------|--------|-------------|
| **Face** | Animated face (full screen), connection dot (top-left) | Internal state machine |
| **Clock** | Large digital time (center), date (below), next reminder preview (bottom), mini face (corner) | RTC or NTP time, reminder schedule from backend |
| **Pomodoro** | Phase label "FOCUS" / "BREAK" (top), large countdown timer (center), cycle dots (bottom), progress bar | Pomodoro state from backend |
| **Reminder** | Icon for reminder type (top), reminder text (center), dismiss hint (bottom) | proactive:reminder event payload |
| **Countdown** | Large countdown number (center), instruction text (below), e.g., "Look far away... 15s" | proactive:reminder with countdown |
| **Status** | Wi-Fi, battery, uptime, conversations today, cache stats | Internal metrics |

Mode transitions:

```
idle timeout → face switches to clock (configurable)
proactive:reminder → switches to reminder mode → auto-returns after durationMs
proactive:pomodoro → switches to pomodoro mode → stays until pomodoro stops
user touch → returns to face mode
voice command "show clock" → clock mode
voice command "show face" → face mode
```
